## Player Routes

### GET /api/players/me
| Rule | Description |
|---|---|
| BR-DATA-03 | Returns the authenticated player's profile (id, name, coins, createdAt) |
| BR-DATA-04 | If player row not found, returns 404 (should not happen after signup, but handled defensively) |

### POST /api/players/coins
| Rule | Description |
|---|---|
| BR-DATA-05 | `amount` must be a positive integer (> 0) and ≤ 1000 per call |
| BR-DATA-06 | Coins incremented via `UPDATE players SET coins = coins + $amount WHERE id = $userId RETURNING *` |
| BR-DATA-07 | Returns updated Player with new coin balance |

### POST /api/players/migrate
| Rule | Description |
|---|---|
| BR-DATA-08 | Receives `{ coins, ownedStickers }` from localStorage |
| BR-DATA-09 | **Q2=A (Merge)**: Sets coins to `GREATEST(current DB coins, provided coins)` |
| BR-DATA-10 | Inserts each sticker ID into `player_stickers` with `ON CONFLICT DO NOTHING` — preserves existing ownership |
| BR-DATA-11 | Returns `{ data: { migrated: true }, error: null }` — always succeeds even if nothing was migrated |
| BR-DATA-12 | Client is responsible for setting `localStorage.setItem("migrationDone", "true")` after success |

## Sticker Routes

### GET /api/players/stickers
| Rule | Description |
|---|---|
| BR-DATA-13 | Returns array of sticker IDs owned by the authenticated player |
| BR-DATA-14 | Returns `[]` if player owns no stickers |

### POST /api/players/stickers (purchase)
| Rule | Description |
|---|---|
| BR-DATA-15 | `stickerId` must be a non-empty string |
| BR-DATA-16 | Route fetches sticker price from `stickers` table; returns 404 if sticker not found |
| BR-DATA-17 | **Q1=B (SQL guard)**: Deducts coins via `UPDATE players SET coins = coins - price WHERE id = $1 AND coins >= price RETURNING coins`. If 0 rows affected → insufficient funds → 400 |
| BR-DATA-18 | After successful deduction, inserts `(player_id, sticker_id)` into `player_stickers ON CONFLICT DO NOTHING` |
| BR-DATA-19 | If sticker already owned (conflict on insert), still returns success with current coin balance — idempotent |
| BR-DATA-20 | Returns `{ newCoinBalance: number }` from the RETURNING clause of the UPDATE |

### GET /api/stickers (catalog)
| Rule | Description |
|---|---|
| BR-DATA-21 | Returns all 22 rows from `stickers` table ordered by category, price |
| BR-DATA-22 | No player-specific data — catalog is shared and immutable at runtime |

|---|---|

### PUT /api/players/canvas
| Rule | Description |
|---|---|
| BR-DATA-25 | `canvasData` is an array of `CanvasItem` objects (validated by CanvasSchema) |
| BR-DATA-26 | Uses UPSERT: `INSERT INTO creative_canvas ... ON CONFLICT (player_id) DO UPDATE SET canvas_data = $data, updated_at = now()` |
| BR-DATA-27 | Returns `apiSuccess(null)` — frontend does not need the updated row back |
| BR-DATA-28 | Frontend debounces saves at 300 ms; backend treats each PUT as authoritative |

## Purchase Atomicity Detail (Q1=B)

The two-step purchase is safe against concurrent double-spend because the WHERE clause
in the UPDATE acts as an atomic check-and-decrement:

```sql
UPDATE players
SET coins = coins - :price
WHERE id = :userId AND coins >= :price
RETURNING coins;
```

- If `coins < price`: WHERE fails → 0 rows returned → application returns 400
- If two concurrent requests arrive: PostgreSQL row-level locking ensures only one
  succeeds at the correct balance; the second will see the already-decremented value
  and fail the WHERE clause

This is equivalent to an optimistic lock at the SQL level and requires no RPC.
