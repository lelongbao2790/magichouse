# Deployment Architecture — Unit 1: SupabaseDBLayer

## Environment Strategy

**Q2 Decision: Remote Only (B)**  
No local Supabase stack required. All migrations apply directly to the linked remote project.
Docker Desktop is not needed.

---

## Environments

| Environment | Database | Auth | Apply Method |
|---|---|---|---|
| Local development | Remote Supabase (`eoelyqphaixgqlkyoxau`) | Remote Supabase Auth | `npx supabase db push` |
| Production | Same remote Supabase | Same remote Supabase Auth | `npx supabase db push` |

> **Note**: For this project, local dev and production share the same Supabase project.
> This is appropriate for a single-developer app. If team isolation is needed in future,
> create a separate Supabase project for staging.

---

## First-Time Setup Sequence

```
1. Copy environment variables
   cp .env.example .env.local
   # Fill in real values from Supabase Dashboard → Project Settings → API

2. Apply migration to remote database
   npx supabase db push
   # Expected output: "Applying migration 0001_initial_schema.sql"

3. Verify migration applied
   npx supabase db remote commit   # (optional — lists remote applied migrations)

4. Apply seed data (run once — idempotent)
   # seed.sql runs automatically on `supabase db reset` (local stack only)
   # For remote: apply manually via Supabase SQL editor or:
   npx supabase db execute --file supabase/seed.sql

5. Generate TypeScript types
   npx supabase gen types typescript \
     --project-id eoelyqphaixgqlkyoxau \
     --schema public \
     > lib/database.types.ts
```

---

## Ongoing Development Sequence

When schema changes are needed (future units):

```
1. Create new migration file
   npx supabase migration new <description>
   # Creates supabase/migrations/YYYYMMDDHHMMSS_<description>.sql

2. Write SQL in the new file
   # Always additive — no DROP in migration files

3. Apply to remote
   npx supabase db push

4. Regenerate types
   npx supabase gen types typescript \
     --project-id eoelyqphaixgqlkyoxau \
     --schema public \
     > lib/database.types.ts
```

## Seed Data Strategy

Seed data (`supabase/seed.sql`) contains the 22 sticker catalog rows. For remote-only
workflow, seed is applied once via the Supabase SQL editor or CLI execute command.

`ON CONFLICT (id) DO NOTHING` ensures re-running the seed is safe if needed.

---

## Artifact Locations

| Artifact | Path | Applied By |
|---|---|---|
| Initial schema | `supabase/migrations/0001_initial_schema.sql` | `npx supabase db push` |
| Seed data | `supabase/seed.sql` | Manual apply (once) |
| DB types | `lib/database.types.ts` | `npx supabase gen types typescript` |
| Security headers | `next.config.ts` | Next.js build / dev server |
| Env template | `.env.example` | Developer copies to `.env.local` |

---

## Dependency on Subsequent Units

`lib/database.types.ts` is generated by this unit and consumed by Units 2–3 (service
modules and API routes). It must be regenerated after any future schema migration.

`next.config.ts` security headers are applied from this unit but the file may be
extended by later units (e.g., adding `rewrites` or `redirects`). Later units must
preserve the `headers()` function added here.
