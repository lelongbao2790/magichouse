# Generate & Run Unit Tests

Produce unit tests derived from spec scenarios and design testing strategy, run them, and fix failures.

## Workflow

### 1. Identify Change Context

```bash
openspec list --json
```

If a change is active, use it. Otherwise ask the user which change to test.

Announce: "Generating tests for change: **<name>**"

### 2. Read Artifacts

Read these files from `openspec/changes/<name>/`:

- **specs/** — Extract all Given/When/Then scenarios. Each scenario = one test case.
- **design.md** — Read the "Testing Strategy" section for:
  - Scenario-to-test-file mapping
  - Required mocks/fixtures/setup
  - Integration vs unit test boundaries
- **tasks.md** — Identify which implementation tasks are complete (to know what code exists to test). Also check if test tasks already contain scenario→test mappings (common when generated by `/opsx:propose`).
- **proposal.md** — Skim for scope boundaries (what's in/out of testing)

Also read the actual implementation files referenced in tasks.md to understand function signatures, types, and packages.

### 2a. Detect UI Changes

Scan the change artifacts and implementation files for UI-related signals:

**Indicators of UI changes:**

- Files under `app/` (routes, pages, layouts), `components/`, `contexts/`, `hooks/`
- Spec scenarios mentioning: browser, page, form, button, click, navigate, URL, screenshot, dashboard, modal, dropdown, input, submit, display, render, visible, UI, route, component, coins, quiz, sticker, theme, language
- Implementation files with extensions: `.tsx`, `.jsx`, `.css`, and `.ts` files under `app/` / `components/` / `contexts/`
- Config files touched: `next.config.mjs`, `tailwind.config.*`, `playwright.config.ts`, `vitest.config.ts`
- API route handlers under `app/api/**/route.ts` that back a UI flow
- References to React contexts (`coin-context`, `language-context`, `theme-context`) or Radix UI primitives

**If UI changes detected:**

1. Announce: "UI changes detected — will generate **unit tests** (Vitest + React Testing Library) AND **Playwright E2E tests**"
2. Split the test plan into:
   - **Unit tests** (Step 3) — component / hook / context / service-level tests run with Vitest (`jsdom`). `*.test.ts` / `*.test.tsx` files under `automation_tests/unit/` (and `automation_tests/api/` for route handlers).
   - **Playwright E2E tests** (Step 3a) — full browser integration tests under `automation_tests/e2e/`.
3. Verify Playwright is available: check for `playwright.config.ts` and `npx playwright --version`

**If no UI changes:** Skip Step 3a entirely and proceed with standard unit tests.

### 2b. Testing Approach — Two Types of Tests

UI changes always produce **two types of tests**:

#### Unit Tests (Vitest + React Testing Library)

`*.test.ts` / `*.test.tsx` files under `automation_tests/unit/` (routes under `automation_tests/api/`) that test components, hooks, contexts, and services in isolation:

- **Component tests** — render with `@testing-library/react`, assert DOM output, fire events, verify context wiring
- **Hook / context tests** — `renderHook`, assert state transitions, check `localStorage` persistence
- **Service / API-route tests** — mock the Supabase client, test business logic and validation, verify response shape
- **Run via**: `pnpm test` (Vitest, `jsdom`), or `pnpm test <pattern>` for a subset, `pnpm test:watch` while iterating
- **Output**: terminal results + coverage in `coverage/` (v8, `lcov` — threshold: 80% lines)

#### Playwright E2E Tests

Full browser integration tests under `automation_tests/e2e/` that exercise complete user flows:

- **E2E test files** in `automation_tests/e2e/*.spec.ts` — navigation, quiz sessions, coin rewards, admin content edits, multi-step flows
- Chromium only (`playwright.config.ts`), headless by default — matches CI. Add `--headed` locally only to watch a failure.
- Needs the dev server running (`pnpm dev` on `http://localhost:3000`, or set `PLAYWRIGHT_BASE_URL`)
- **Run via**: `pnpm test:e2e` (or `npx playwright test automation_tests/e2e/<file>.spec.ts --reporter=list`)

### 3. Build Test Plan

**If tasks.md already contains scenario→test mappings** (e.g., task 12.1 lists "Scenario X → TestY"), use those as the plan. Announce the plan and proceed — don't re-ask for confirmation.

**If no pre-existing mappings**, build the plan from spec scenarios:

| Scenario  | Test Name    | Test File                              | Module Under Test | Mocks Needed |
| --------- | ------------ | -------------------------------------- | ----------------- | ------------ |
| From spec | `it('...')`  | `automation_tests/unit/<feature>.test.ts` | `lib/...` / `contexts/...` | list |

**Mapping rules:**

- One scenario → one `it(...)` block (1:1)
- Scenario name → the `it(...)` description, verbatim where readable
- Group tests by the **module they exercise** (not the spec they came from), inside a `describe(...)` block
- Include error-path and edge-case scenarios from specs
- Property-based scenarios ("for all inputs…") → a `.pbt.test.ts` file using `fast-check` (see existing `automation_tests/unit/*.pbt.test.ts`)

**Test file placement:**

- Create **change-scoped test files** named after the feature (e.g., `automation_tests/unit/daily-challenge.test.ts`) rather than appending to existing large test files. This avoids merge conflicts and makes change traceability clear.
- API route handlers → `automation_tests/api/<route>.api.test.ts`.
- Exception: if a small existing test file clearly owns this area, append to it.

Follow the existing patterns — scan `automation_tests/unit/` and `automation_tests/api/` for the closest example before writing.

Present the plan to the user only if it was built from scratch (not pre-mapped in tasks.md):

```
## Test Plan for <change-name>

Found N spec scenarios to cover:

### Unit (automation_tests/unit/)
1. resolves fixed-content subject → subject-content.test.ts
2. rejects an out-of-range correct_index → admin-validation.test.ts

### API (automation_tests/api/)
3. GET /api/subjects/[key]/questions returns active questions → subject-questions-route.api.test.ts

Mocks needed:
- Supabase client (query builder)

Proceed with test generation? (y/n)
```

### 3a. Build Playwright E2E Test Plan

Only if UI changes were detected in Step 2a. This produces **E2E tests** that complement the unit tests from Step 3.

**Every UI change must have BOTH:**

1. **Unit tests** (Step 3) — component / hook / context / service-level, run via Vitest
2. **Playwright E2E tests** (this step) — full-browser integration tests in `automation_tests/e2e/`

**Identify E2E scenarios** from specs — any scenario involving end-to-end user flows:

- Page navigation, form submission, button clicks
- Content rendering, visibility checks, layout assertions
- Error messages displayed to users
- Multi-step browser workflows (navigation, search, grid interactions)
- Route transitions, data loading, grid filtering

**Map E2E scenarios to Playwright tests:**

| Scenario  | Test Name                    | Test File                              | Assertions            |
| --------- | ---------------------------- | -------------------------------------- | --------------------- |
| From spec | `test('scenario name', ...)` | `automation_tests/e2e/feature.spec.ts` | visibility, URL, text |

**Test file placement:**

- Place E2E test files in `automation_tests/e2e/` (matches `playwright.config.ts` `testDir`)
- Follow existing patterns in `automation_tests/e2e/*.spec.ts` (`smoke.spec.ts`, `grade2-subjects.spec.ts`)
- There is no auth setup project — if a flow needs a signed-in player, do the login/onboarding in the test (or a `beforeEach`), matching how the existing specs handle it
- Read `playwright.config.ts` for config (base URL `http://localhost:3000` or `PLAYWRIGHT_BASE_URL`, Chromium only, headless)

**Generate Playwright E2E test files:**

```typescript
import { test, expect } from "@playwright/test";

// Scenario: <scenario name from spec>
// Spec: specs/<spec-name>/spec.md
test.describe("<feature name>", () => {
  test("<scenario name>", async ({ page }) => {
    // GIVEN - navigate and setup
    await page.goto("/<route>");

    // WHEN - user action
    await page.getByRole("button", { name: "Submit" }).click();

    // THEN - assertions
    await expect(page.getByText("Success")).toBeVisible();
  });
});
```

**Writing accurate locators:**
Prefer role-based locators: `getByRole`, `getByText`, `getByLabel`. Radix UI primitives expose good ARIA roles — use them rather than CSS selectors.

**Run E2E tests:**

```bash
# All E2E tests (needs the dev server running)
pnpm test:e2e

# One file
npx playwright test automation_tests/e2e/feature.spec.ts --reporter=list

# Watch a failure in a real browser (local only)
npx playwright test automation_tests/e2e/feature.spec.ts --headed
```

The suite runs **headless by default** (matches `playwright.config.ts` and CI). Use `--headed` only locally to observe a failing test.

E2E test failures feed into Step 6 (Fix Failures) alongside unit test failures.

### 4. Generate Test Files

For each test file:

1. Check if the file already exists — if so, append new tests, don't overwrite existing ones
2. Reference `template.md` in this skill folder for the **reporting format** when presenting results (it is a documentation template for reporting, not a code generation template)
3. Write idiomatic test code for Vitest + TypeScript:
   - Follow existing test patterns in `automation_tests/unit/` and `automation_tests/api/`
   - Use Vitest globals (`describe`, `it`, `expect`, `vi`) — they're enabled in `vitest.config.ts`
   - Use `it.each([...])` for table-driven cases; `fast-check` (`fc.assert`, `fc.property`) for property-based cases
   - Import app modules via the `@/` alias (e.g. `import { resolveSubjectContent } from "@/lib/services/..."`)
   - Add a comment linking each test back to its spec scenario

**Test structure (Vitest unit):**

```ts
// Scenario: <scenario name from spec>
// Spec: openspec/changes/<name>/specs/<spec-name>/spec.md
import { describe, it, expect } from "vitest";

describe("<feature name>", () => {
  it("<scenario name>", () => {
    // GIVEN - setup
    // WHEN - action
    // THEN - assertions
    expect(actual).toEqual(expected);
  });
});
```

**Test structure (component / hook):**

```tsx
import { render, screen } from "@testing-library/react";
import { renderHook, act } from "@testing-library/react";
// wrap in the needed context Provider(s); assert DOM or hook state
```

**Test structure (API route):**

```ts
// mock the Supabase client, build a Request, call the exported GET/POST handler,
// assert response.status and the parsed JSON body
```

### 5. Run Tests

Execute tests for the affected packages. **Before running, establish a baseline** to separate pre-existing failures from new ones:

#### 5a. Baseline Pre-Existing Failures

Run the affected packages' existing tests first (without your new tests if possible) or check CI history for known failures. Record any pre-existing failures so they don't pollute your results.

#### 5b. Run New Tests in Isolation

Use file / name-pattern filters to run only your new tests:

```bash
# By file
pnpm test automation_tests/unit/daily-challenge.test.ts

# By test-name substring
pnpm test -- -t "resolves fixed-content subject"
```

#### 5c. Full Suite Run

Then run the whole unit/API suite to confirm nothing regressed:

```bash
pnpm test                 # all unit + api tests (vitest run)
pnpm test:coverage        # with coverage (threshold: 80% lines)
```

For UI changes, also run the relevant E2E spec (Step 3a).

#### 5d. Handle Blockers

If a test cannot run due to something outside this change (missing env var like `SUPABASE_SERVICE_ROLE_KEY` for an integration test, dev server not up for E2E, a `tsc` error in unrelated code):

- **Do NOT** count it as a test failure or loop trying to fix it
- Isolate: `pnpm exec tsc --noEmit` to see if it's a type error; `pnpm lint` for lint issues
- Create the test file anyway — it documents intent and will run once the blocker is resolved
- Report it as **"blocked"** with the specific reason, not "failed"
- Document the blocker in tasks.md

Capture output. Parse results into:

- **Passed**: tests that ran and succeeded
- **Failed**: tests that ran and failed (separate pre-existing vs new)
- **Blocked**: tests that couldn't run due to external issues

### 6. Fix Failures (Loop)

If tests fail:

1. Read the failure output
2. **First, determine if the failure is pre-existing:**
   - Check `git log` on the failing test file — was it modified in this change?
   - If feasible, run the same test on `main`
   - If pre-existing: note it in the report, do NOT count it against this change, do NOT try to fix it
3. For failures in our changes, determine root cause:
   - **Test code** (bad assertion, wrong setup, wrong mock) → fix the test
   - **Implementation code** (actual bug found by test) → fix the implementation to match the spec
   - **Missing mock/dependency** → add the mock (`vi.mock(...)`, `vi.fn()`)
4. Re-run only the affected tests after each fix (`pnpm test <file>` or `-t <name>`)
5. Loop until all _our_ tests pass or stalled

**Fix priority**: Prefer fixing implementation to match the spec over weakening tests. The spec is the source of truth.

#### 6a. Self-Correction Loop (Implementation Fixes)

When a test failure reveals a bug in **implementation code** (not test code):

1. **Analyze the failure** — Read the error message, stack trace, and expected-vs-actual values
2. **Locate the source** — Find the implementation function that produced the wrong result
3. **Read the spec** — Re-read the Given/When/Then scenario to confirm the expected behavior
4. **Fix the implementation** — Edit the source file to match the spec's expected behavior
5. **Re-run only the failing test** — Verify the fix works
6. **Regression check** — Run the full package to ensure the fix didn't break other tests

**Self-correction rules:**

- Only fix implementation code that was created/modified as part of this change (check `git diff` against the base branch)
- Never fix code outside the change scope without user confirmation
- If the fix would change a public API signature, pause and ask the user
- If the fix contradicts the spec, the spec wins — ask the user to clarify
- Log every implementation fix in the report (Step 7) with before/after snippets

**For unit test failures (UI components / hooks / contexts):**

- Read the Vitest failure output — expected vs actual, stack trace, the failing `expect`
- Fix component logic, context/hook state, or test setup (missing Provider wrapper, un-awaited state update) as needed
- Re-run after each fix: `pnpm test <file>`

**For Playwright E2E test failures:**

- Re-run the failing spec, adding `--headed` locally to watch it:
  ```bash
  npx playwright test automation_tests/e2e/feature.spec.ts --headed --reporter=list
  ```
- Check the HTML report (`playwright-report/`) and `test-results/` for details (enable `trace`/`screenshot` in `playwright.config.ts` temporarily if needed)
- Fix rendering logic, event handlers, or API responses as needed
- Re-run the spec after each fix

**Max iterations**: 5 automatic fix attempts per test. After 5, pause and report:

```
## Test Fixes Stalled

After 5 fix attempts, these tests still fail:
- TestXxx: <reason>
- Root cause analysis: <what the agent has tried and why it's stuck>
- Implementation fixes attempted: <list of changes made>

Options:
1. Show me the failing test details and attempted fixes
2. Let me provide guidance, then retry
3. Skip this test for now and continue
```

### 7. Report Results

Separate our results from pre-existing issues:

```
## Tests Complete for <change-name>

**Results**: N/N passing ✓ (M blocked, K pre-existing failures noted)

### Spec Coverage
| Scenario | Test | File | Type | Status |
|----------|------|------|------|--------|
| Resolves fixed-content subject | `it('resolves fixed-content subject')` | automation_tests/unit/subject-content.test.ts | Unit | ✓ Pass |
| Rejects out-of-range correct_index | `it('rejects out-of-range correct_index')` | automation_tests/unit/admin-validation.test.ts | Unit | ✓ Pass |
```

### 8. Update Task Checkboxes

Mark completed test tasks in `openspec/changes/<name>/tasks.md`:

- `- [x] Generate unit tests derived from spec scenarios`
- `- [x] Run tests and capture results`
- `- [x] Fix any test failures` (if applicable)
- `- [x] Verify all tests pass`

When tests are blocked (not failed), still mark the task complete with a note explaining why:

- `- [x] 12.2 Generate unit tests for X — blocked: reason. Test file created for when deps are resolved.`

## Instructions

### Always Do

- Read spec scenarios before writing any test code
- Map every scenario to an `it(...)` / `test(...)` block (1:1 traceability)
- Follow existing test patterns in `automation_tests/unit/`, `automation_tests/api/`, `automation_tests/e2e/`
- Comment each test with its source scenario
- Create change-scoped test files (e.g., `automation_tests/unit/<feature>.test.ts`) to avoid merge conflicts with other branches
- Run tests after generating them — never skip execution
- Establish a baseline of pre-existing failures before attributing any failures to this change
- Use file paths / `-t <name>` filters to isolate new tests from pre-existing failures
- Fix test failures before reporting success — fix implementation code (self-correct) rather than weakening assertions
- When a test reveals an implementation bug, fix the source code, not the test
- Scan for UI changes before building the test plan — UI changes require BOTH unit tests AND Playwright E2E tests
- For unit / API tests, run via `pnpm test` (Vitest) and read terminal output for pass/fail
- For E2E tests, run via `pnpm test:e2e` (headless, matches CI); use `--headed` only locally to debug
- Log all self-corrected implementation fixes in the report with before/after context
- Update task checkboxes in tasks.md
- Keep tests in TypeScript — this is a single-language (TS) project

### Ask First

- If a scenario is ambiguous or untestable as written
- If implementation code doesn't exist yet for a scenario
- If fixing a test failure requires changing implementation code beyond the scope of this change
- If the testing strategy in design.md conflicts with spec scenarios

### Never Do

- Generate tests without reading the specs first
- Write tests that don't trace back to a spec scenario
- Skip running the tests after generation
- Weaken test assertions to make tests pass — fix the implementation instead (self-correct)
- Overwrite existing test files — append or modify instead
- Mark test tasks as failed when they are blocked by external dependencies — use "blocked" status with explanation instead
- Count pre-existing test failures as failures of this change
- Loop trying to fix type/lint errors in code outside this change's scope
- Run only `pnpm test` with no filter while iterating — use a file path or `-t <name>` to isolate new tests
- Self-correct implementation code that is outside the scope of this change without user confirmation
- Skip UI test generation when UI changes are clearly present — every UI change needs BOTH unit tests AND Playwright E2E tests
- Add `--headed` (or disable `headless`) in a way that lands in a commit — the suite is headless by default
- Skip unit tests for UI changes and only write E2E tests — both are required
- Skip E2E tests for UI changes and only write unit tests — both are required
